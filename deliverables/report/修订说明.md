4. **提炼四条创新点（1.4），措辞克制**。不出现“首次”“新漏洞”。四条分别是：①分层证据模型加 MDE；②预注册与可审计锁频，并给出“锁频的价值在于确定性而不在于降噪”这一反直觉结论；③多工具交叉加 90 格排查，发现 272125f 产物里残留与 clangover 同源的分支（标明是历史提交上的机制层观察，只作为候选解释）；④优化级别与跨环境对照。

## 三、从评审角度看仍然存在的短板

**影响评奖等级的硬伤：**

1. ~~**没有网络或远程实验**~~ → **已于 2026-10-21 补做**（T25 同机网络场景：裸金属真实两端 + 匿名 netns + 自有 veth + 内核 netem 三档，证据 `docs/evidence/r13-network-20261020/`）。
   **结论上限仍须照写**：网络各档在本预算下**一律未检出**，本地直调档 M1 未修臂两次运行一次可分辨、一次未检出，跨运行可分辨性不稳定；本轮每类 2000 样本比「分辨该量级所需样本数」少 4～5 个数量级，因此只写「本预算下未检出」，**不写「没有远程泄露」**。
2. **防护以采纳上游修复为主，自主防护不足**。题面第 6 条要求“针对已发现问题采用……进行修改”。真实缺陷全部采用官方补丁，团队自己写的修复只有人工夹具 M3/M4。更要紧的是，报告自己发现了 272125f 里残留的 poly_frommsg 分支，却**没有给出修复和复测**。评委很可能追问这一点。
3. ~~**只有单一 CPU 架构**~~ → **已于 2026-10-21 补做第二架构**（真实 aarch64 容器内原生 12 格，证据 `docs/evidence/r15-aarch64-20261021/`）。
   aarch64 侧 12 格**全部 0 错误 / 0 上下文**，反汇编给出 `sbfx`/`csel`（无分支）对比 x86_64 的 `bt`+`jae`，
   即 **M1 的泄漏机制是 x86_64 特定的编译器产物**。**边界**：aarch64 侧未锁频、非裸金属，只构成第二个架构、**不构成第二个测量机**，时间证据不跨架构合并。
   **仍未做**：GCC 对照与 -O1/-Oz/-Og（属「未执行」，不写成「未检出」）。
4. **M2 的计时实验设计偏弱**。类对不是针对除法操作数设计的；每类是同一份密文重复 10000 次，单次运行的区间只反映测量噪声；MDE 达 25–67 ns，远大于除法可能产生的效应。M2 计时“未检出”的说服力有限。另外还有一个未解释的问题：M2 存在与 M1 相同的 bt/jae 分支，为什么在 M2 上没有检出？

**中等短板：**

5. 计时分辨率约 10 ns（CLOCK_MONOTONIC），没有用 rdtscp；没有配置 isolcpus，SMT 开启，后台有 39 个服务。
6. ~~M5 重加密步骤的 Binsec 结果是 unknown~~ → **已于 2026-10-21 闭合**（`docs/evidence/r14-binsec-m5-20261021/RESULT.md`）：
   i386 裸机驱动 + 显式 `secret global` 建模，FO 重加密比较步骤 1088/1088 路径完成、消息编码步骤 1/1 路径完成，
   均无秘密相关控制流；同配置下 M4 已知脆弱内核报 insecure，**证明不假阴性**。
   **边界**：只回答「控制流是否依赖秘密」，不覆盖整个解封装的其它性质。Microwalk 只跑了 M3，没有用上官方镜像。Binsec 只跑了 M4 抽取内核，且没有开启乘除法检查。
7. 题面高水平项“面向 CI 的时间侧信道回归测试工具”没有实现。
8. M1 是前期封存的数据，复测的锁频规程与 M2–M5 是同一套，但不是同一批采集。M1 的预注册证据链（计划冻结时间）需要能在答辩时说清楚。
