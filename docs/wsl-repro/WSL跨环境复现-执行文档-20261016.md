## 2. WSL 前置检查

**这一节由队友在 Windows 侧完成，AI 可以提醒。**

1. **电源**：
   - 插上电源；
   - Windows 设置 → 系统 → 电源 → 电源模式选“最佳性能”；
   - 笔记本关掉省电模式。
2. **关闭大程序**：浏览器多标签、游戏、IDE 索引、杀毒全盘扫描、OneDrive 同步，能关就关。
3. **WSL 版本**：在 PowerShell 里运行 `wsl -l -v`，确认 Ubuntu 的 VERSION 是 **2**。如果是 1，执行 `wsl --set-version Ubuntu 2`。【未在 WSL 实测】
4. **`.wslconfig` 建议**：放在 `C:\Users\<你的用户名>\.wslconfig`，改完在 PowerShell 执行 `wsl --shutdown` 再重开。【未在 WSL 实测】
   ```ini
   [wsl2]
   processors=4        ; 给 WSL 至少 4 个逻辑核（核多的机器可以给到总数-2）
   memory=8GB          ; 至少 6GB
   swap=4GB
   ```
5. **磁盘位置**：所有工作必须放在 WSL 的 ext4 家目录，例如 `~/cry-wsl`，**不要放 `/mnt/c/...`**。那是 9p 网络文件系统，构建慢、计时噪声大，脚本检测到会直接退出。
   - 磁盘空间需要 ≥ 10 GB：全量原始 CSV 约 1.5–2 GB，构建约 2 GB。
6. **发行版**：推荐 Ubuntu 24.04，apt 自带 `clang-18`。Ubuntu 22.04 没有 clang-18 包，见第 10 节 Q2。

AI 在 WSL 里先执行：
```bash
cat /proc/version          # 应含 microsoft / WSL2
lsb_release -a             # 记录发行版
nproc; free -h; df -h ~
```

## 3. 环境安装与仓库获取

### 3.1 仓库可见性（已核实）
在无凭据条件下执行 `GIT_TERMINAL_PROMPT=0 git ls-remote https://github.com/Gowin-liuyin/cryProject.git HEAD`，能返回 `04baad45ebb5…`。因此 **仓库是公开的**，直接 clone，不需要 final5 匿名包。

如果到执行那天仓库被设为私有，clone 会要求输入密码。这时改用匿名包，见第 10 节 Q1。

### 3.2 一键执行（推荐）
```bash
cd ~
chmod +x wsl_repro.sh
# 先试跑：每类 2000、每种子 1 次，约 10 分钟，用来确认流程能走通
QUICK=1 WORK=~/cry-wsl-quick ./wsl_repro.sh all
# 试跑没有错误（检查 ~/cry-wsl-quick/out/ERRORS.tsv 是否不存在或为空）后，再做正式全量：
WORK=~/cry-wsl ./wsl_repro.sh all
```

脚本分阶段执行：`check → deps → fetch → build → env → verify → p0m1 → p0m5 → p1opt → p1perf → p2m4 → p2m2 → stats → pack`。

- 每个阶段完成后会写 `out/.stamps/<阶段>.done`。中断后重新执行同一条命令就会自动续跑；单个采集文件已存在的也会跳过。
- 想重做某个阶段，用 `FORCE=1 ./wsl_repro.sh <阶段>`。
- `./wsl_repro.sh status` 查看已完成的阶段和错误记录。
- 所有输出同时写入 `out/logs/wsl_repro-<时间>-<阶段>.log`。

可调的环境变量：

| 变量 | 默认 | 含义 |
|---|---|---|
| `WORK` | `~/cry-wsl` | 工作根，必须在 ext4 上 |
| `CPU` | 最后一个逻辑核 | `taskset -c` 的绑核编号。在 WSL 里这是 vCPU，不对应固定物理核 |
| `SAMPLES` | 20000（QUICK=1 时为 2000） | 每类样本数，上限 20000（由 measure 程序限定） |
| `REPEATS` | 3（QUICK=1 时为 1） | 每个种子重复几次 |
| `CC_BIN` | `clang-18` | 编译器 |

### 3.3 各阶段实际做了什么（AI 排障时看这里）

**deps**：
```bash
sudo apt-get install -y clang-18 llvm-18 cmake make git curl ca-certificates patch valgrind binutils util-linux python3 openssl perl procps
```
实测时 apt 镜像曾临时返回 500，脚本对 `apt update` 失败只打印警告，不中止。

**fetch**：
- `git clone` 仓库并 `checkout 04baad4`。
- **处理 BLOCKERS B05**（干净 clone 缺少被 `.gitignore` 排除的第三方件）：
  - `sh tools/fetch_liboqs_0.10.0.sh`：下载 liboqs 0.10.0 并校验 SHA-256 `2b7b4436…`，放到 `vendor/liboqs-0.10.0/`。
  - 复制一份到 `vendor/liboqs-0.10.0-982c762/`，打上官方修复补丁，补丁地址是 `https://github.com/open-quantum-safe/liboqs/commit/982c762c242ef549c914891b47bf6e0ed6321f91.patch`。实测补丁 sha256 为 `d1879ac6…6376`，GitHub 生成的 patch 头部可能会变，所以只记录、不强校验；脚本改用“补丁后 `poly.c` 含 `cmov_int16`”和后面的反汇编 `setb` 来确认。
    - 仓库里没有在本地生成修复树的脚本，nss-marker 上的修复树是手工生成的，见 `docs/evidence/liboqs010-locked-20261015/README.md`。这一步是本文档补上的最小做法，没有改动任何仓库源码。
  - `sh docs/evidence/m2-kyberslash-20261016/version-audit/fetch_vendor.sh`：取 M2 两版 Kyber（a621b8d / 272125f），带 tar 摘要校验。
  - `git clone https://github.com/oreparaz/dudect` 并 checkout `dc269651…`（仓库 REPOS.md 钉住的版本）到 `third_party/dudect/`。CMake 检测到它之后，会自动多编 `platform_m4_dudect_*`、`platform_m5_dudect` 和 `platform_dudect_replay`。
  - RTLF 需要 R 和 tidyverse，体积大，**默认不装**。统计电池会如实写 `RTLF unavailable`，不推断结果。

**build**：
- 平台构建：
  ```bash
  cmake -S repo -B build/platform -DCMAKE_C_COMPILER=clang-18 -DOPENSSL_EXECUTABLE=$(command -v openssl) -DBASELINE_ENABLE_PLATFORM=ON -DA113_ARCHIVED_CASE_ONLY=OFF
  cmake --build build/platform -j8
  ```
- M1 两版（`-Os`）：
  ```bash
  cmake --preset historical-clangover -B build/m1-<unfixed|fixed>-Os -DCMAKE_C_COMPILER=clang-18 -DLIBOQS010_SOURCE_DIR=<对应 vendor 目录> "-DLIBOQS010_C_FLAGS=-Os -fno-vectorize"
  ```
  - preset 里写的是 `CMAKE_C_COMPILER=clang`，Ubuntu 默认可能没有 `clang` 这个名字，所以显式改成 clang-18。
  - liboqs 的 AVX2 关闭、generic 目标等参数，已经由 `cmake/Liboqs010Historical.cmake` 固定。

### 3.4 关于“锁频控制器”：不需要绕过
- 仓库的锁频控制器 `tools/platform_control/controller.py` 只是**外层包装**。它要求 sudo、写 sysfs，并要求控制根在 `<...>/Cry` 下。真正采数的是各个 `measure` 程序。
- 程序本身不调频，meta 里固定写 `frequency_control=not_configured`、`cpu_affinity=not_pinned`。
- 因此 WSL 流程**完全不调用控制器**，直接用 `taskset -c $CPU <measure> RUN_ID SEED SAMPLES CSV META` 运行。命令形态和 `docs/evidence/r09-optlevel-20261016/RUNS.sh` 里 `--` 之后的 worker 命令逐字一致。
- **不需要打任何补丁，也不改源码。**
- `scripts/reproduce_all.sh quick` 同样不锁频、不用 sudo，可以作为额外的自检。它的 `full --execute` 必须有控制器，**不要在 WSL 用**。

## 5. 采集实验清单

通用设置：
- 种子 `31337 / 424242 / 7`，每个种子重复 `REPEATS` 次（默认 3）。
- 每类 `SAMPLES` 次（默认 20000）。每次运行同时采 5 类（valid / bit-flipped / random / message-zero / message-ones），主比较是 **message-zero vs message-ones**。
- 程序内部有 100 次预热，并做类别乱序（`balanced_fisher_yates`）。
- 全部 `taskset -c $CPU`，计时用 `CLOCK_MONOTONIC`（ns）。
- 耗时按本机实测 ×1.5 估算；WSL 通常比本机云 VM 更安静，但不保证。

## 6. 必须记录的环境数据

`./wsl_repro.sh env`（`all` 和 `pack` 会自动调用）会写入 `out/env/ENV.txt`，包括：
- **Windows 版本**：`cmd.exe /c ver`。
- **电源计划**：`powercfg /getactivescheme`。
- **CPU 型号、核数、主频**：PowerShell `Win32_Processor`。
- **是否插电**：`Win32_Battery`。
- **WSL 版本**：`wsl.exe --version`。
- 以上依赖 WSL 的 Windows 互操作，**【未在 WSL 实测】**；在本机 VM 上会如实打印“不可用”。
- `uname -a`、`/proc/version`（WSL 内核）、`/etc/os-release`、`lscpu`、`nproc` 与绑核编号、`free -h`、`df -h`。
- clang、gcc、cmake、valgrind、python、openssl 的版本。
- 计时源：`/sys/devices/system/clocksource/clocksource0/current_clocksource`，以及 meta 里的 `clock=CLOCK_MONOTONIC`、`clock_resolution_ns`。
- 频率管理状态：cpufreq 目录是否存在（WSL2 下通常不存在，所以写“未锁频、未关 boost”）。
- 负载：`uptime`、占用最高的 15 个进程。
- `.wslconfig` 内容。
- 仓库 HEAD 与 `git status --short`（应只有 vendor、third_party 这类被忽略的取件，不能有源码改动）。
- **频率快照**：每次采集前后，向 `out/env/freq_snapshots.txt` 追加 `/proc/cpuinfo` 的 `cpu MHz` 行和 `uptime`。在 WSL 中这个值可能是常数或宿主名义频率，只作参考。

还需要队友手工补进 RESULT.md 的内容（AI 应主动询问）：
- 电源模式截图或文字；
- 是否插电；
- 采集期间是否用过电脑。

## 7. 统计分析（stats 阶段）

1. **仓库自带统计电池**：
   - 对每个原始 CSV 执行 `scripts/run_stats_battery.sh --input <csv> --format measure --classes message-zero message-ones --output-dir out/stats/runs/<run> --stats-bin build/platform/platform_stats`，M4 的类别是 `mismatch-first mismatch-last`。
   - 输出 `ci_welch.json`：
     - Δ = **class0 − class1**；
     - 95% 正态近似 CI；
     - Welch t、自由度、双侧 p；
     - `dropped_tail_count=0`，即不删尾。
2. **汇总脚本** `out/analyze_wsl.py`（脚本自动生成，只用 Python 标准库）：
   - 逐次运行：Δ、CI、p，并与电池的 Δ 逐行对照，两列应完全相等（实测一致）。另给中位数差、p90 差、p99 差，分位数下标取 `floor(p(n-1)+0.5)`，与 `docs/reference-benchmark.md` 第 50 行口径一致。
   - 按臂固定效应逆方差合并：合并 Δ、95% CI、z，以及“同号运行数”。
   - 性能表：均值、中位数、p90、p99；M1 decaps 开销% =（已修 ÷ 未修 − 1），附 bootstrap 1000 次 CI（种子 2026）。
   - dudect：各日志最后的 max t 和终止状态。阈值 t>10，族外。
   - 汇总写入 `out/stats/SUMMARY.md`。
3. **符号方向（务必写清）**：
   - M1、M2、M5：**Δ = mean(message-zero) − mean(message-ones)**。Δ>0 表示全 0 消息解封装更慢。
   - M4：Δ = mean(mismatch-first) − mean(mismatch-last)。vulnerable 臂应为负，因为第一个字节就不同，提前退出更快。
   - nss-marker 的已有数值方向见第 9.3 节，比较时只看**方向是否一致**和**是否可区分**，不比较绝对 ns。
4. **dudect 离线回放**（`platform_dudect_replay`）：实测在每类 10000 条时仍返回 `insufficient_measurements`，因为它会丢掉第一批 10000 条。因此脚本以**在线 dudect** 为准，不使用离线回放。

## 9. 解读口径（AI 写 RESULT.md 必须遵守）

1. **只作跨环境描述，不进 Holm**。WSL 的结果没有冻结 PLAN、没有锁频，不进入任何 Holm 家族，也不改变主报告中 M1–M5 的判定。
2. **未检出不等于安全**。本机 VM 实测中，M1 主比较的单次 SE 约为 100–500 ns，而 nss-marker 上的效应只有约 25–40 ns，**大概率测不出**。这是噪声底限，不是“修复后的样子”。
3. **不与裸金属数据合并**。不把 WSL 的 Δ 和 nss-marker 的 Δ 放进同一个合并估计或同一个 CI。
4. **确定性证据和计时证据分开写**：
   - 反汇编和 Memcheck 与噪声无关，应当与 nss-marker **逐项一致**：
     - 未修 `-Os` 为 `bt+jae`、Memcheck 1 context；已修为 `bt+setb+call cmov_int16`、0/0。
     - `-O2` 为 8 个 context；`-O3` 为 15 个；`-O0` 为 0/0。
     - 本机已复现 `poly.c:179`，结果完全一致。
   - 这是 WSL 上**最有价值**的跨环境证据。
5. **M3、M4 是人工构造校准**，写它们时必须带这个标注；M4 只报分臂数值。
6. 不得把单次 p<0.05 写成“检出”，要看三个种子和全部重复的合并结果以及方向一致性。
7. **本机 QUICK 试跑的参考结果**（每类 2000，非正式，只说明流程可用）：
   - 确定性证据：Memcheck 未修 `-Os`/`-O2`/`-O3` 为 512 errors，分别来自 1/8/15 个 context；已修全部 0/0；未修 `-O0` 也是 0/0。
   - M4 人工构造校准，vulnerable 臂合并 Δ = −15.54 ns [−15.77, −15.32]，dudect max t = +765；ct 臂 Δ = −0.07 ns [−0.16, +0.03]，dudect max t = +1.43。
   - M1 `-Os` 未修合并 Δ = +307 ns [+107, +507]（3 次，每类 2000）。量级是裸金属的 10 倍，很可能主要是虚拟化噪声，**不作结论**，正式全量后再看。
   - M5 各级合并 CI 都含 0。
   - 性能：已修反而比未修快约 7%。这是不锁频加不同二进制布局的结果，**不能解读为“修复带来加速”**。

### 9.3 已有裸金属数值与“M1 Δ 符号方向”核查结论（供比较方向时参考）
- 定义一致：
  - `liboqs010-locked-20261015`、`r02-r04-close-20261016` 和 `r09-optlevel-20261016/result.csv` 的 Δ 都是 **mean(message-zero) − mean(message-ones)**；
  - r09 的 CSV 列为 `mean_message_zero_ns, mean_message_ones_ns, delta_ns`，s1 的 55527.77 − 55548.48 = −20.70。
- 但方向相反：
  - 早先冻结 ELF（`measure` sha256 `bd84ee9c…`，`-Os`）三次运行为 +39.34 / +31.12 / +22.34，合并 **+32.311** [20.28, 44.34]；
  - r09 重建的 `m1unfixed-Os`（digest `b71073a6…`）为 −20.70 / −12.51 / −53.47。
  - 两者是**不同二进制**，r09 是按 compile_commands 只替换 -O 后重建的归档。同一机制在两次构建上给出相反方向。
- r09 RESULT.md 第 168–169 行用“bit=0 跳过一次 2 字节存储，所以全 0 更快”来论证负号“与机制自洽”。但按这个论证，早先的 +32.3 就成了“反机制”。这说明端到端 Δ 的**符号受二进制布局、对齐等因素主导**，不能用分支代价模型解释符号。**结论只能依据“可区分”，不能依据符号。**
- **另一个问题**：r09 表中 `Δ̄ [CI]` 一列的方括号其实是三个种子 Δ 的**最小值到最大值**，不是 95% CI。例如 `-Os` 的 [−53.47, −12.51] 正好是 s3 和 s2 的 Δ。
  - 我用同一份 result.csv、各种子自身 CI 反推 SE，做了逆方差固定效应合并：
    - `m1unfixed-Os` = **−26.16 [−37.51, −14.81]**，仍然不含 0；
    - `m1unfixed-O0` = +26.25 [−1.42, +53.92]；
    - `m1fixed-O0` = −25.75 [−51.59, +0.09]。r09 正文第 193 行称其“合并 CI 不含 0”，按真合并其实**刚好含 0**；
    - `m1fixed-O3` = −10.38 [−21.77, +1.00]。
  - 建议在主仓库修正 r09 表头（改为“种子 Δ 范围”，或换成真合并 CI），并在报告中把 M1 符号表述改为“方向随构建变化，判定只依据可区分性”。这需要主仓库另起一轮修改，**WSL 执行员不要动主仓库**。

## 10. 常见问题排障

| # | 现象 | 处理 |
|---|---|---|
| Q1 | `git clone` 要求密码（仓库变私有）或网络不通 | 改用匿名包 final5：把 zip 放到 `~/`，解压到 `~/cry-wsl/repo`，然后 `git init && git add -A && git commit -qm snapshot`（只在本地，满足 meta 的 git 要求），再执行 `FORCE=1 ./wsl_repro.sh fetch` 补取件（脚本会跳过 clone）。【未实测】 |
| Q2 | Ubuntu 22.04 没有 `clang-18` 包 | 用官方 apt 源：`wget https://apt.llvm.org/llvm.sh && sudo bash llvm.sh 18`，然后重跑 deps。实在不行就用 `CC_BIN=clang-15` 或更高（clangover 影响 Clang 15–18），并在 RESULT.md 注明编译器不同。【未实测】 |
| Q3 | `apt update` 报 500 或签名错误 | 镜像临时故障，脚本只告警。等几分钟后执行 `FORCE=1 ./wsl_repro.sh deps`。（本机实测遇到过一次） |
| Q4 | `fetch_liboqs_0.10.0.sh` 报 `shasum: not found` | `sudo apt install -y perl`（shasum 属于 perl），然后重跑 fetch |
| Q5 | `refusing to overwrite unexpected tree` / `fetch_vendor.sh` 拒绝覆盖 | 说明上次取件残缺。删除 `~/cry-wsl/repo/vendor/<对应目录>` 后执行 `FORCE=1 ./wsl_repro.sh fetch` |
| Q6 | 打 982c762 补丁失败 | 删除 `vendor/liboqs-0.10.0-982c762` 后重跑 fetch；检查 `out/env/liboqs-982c762.patch` 是否是 HTML（网络被拦截）。可以改用 `git clone https://github.com/open-quantum-safe/liboqs && git -C liboqs diff 982c762~1 982c762 > patch` 生成同一补丁 |
| Q7 | `cmake --preset` 报 `CMAKE_C_COMPILER clang not found` | 脚本已经传了 `-DCMAKE_C_COMPILER=clang-18`；手工执行时也要加 |
| Q8 | `taskset: failed to set pid's affinity: Invalid argument` | `CPU` 超出范围。用 `nproc` 查核数，设 `CPU=<nproc-1>` |
| Q9 | Valgrind 报 `unhandled instruction` 或非常慢 | Valgrind 3.22 及以上可以；Ubuntu 24.04 自带 3.22。Memcheck 每次约 10 秒属正常 |
| Q10 | 计时 CSV 中出现几十万 ns 的离群值 | 正常（虚拟化抢占）。**不要删**；主统计不删尾，另看中位数和分位数差 |
| Q11 | `platform_dudect_replay` 显示 `insufficient_measurements` | 预期行为（见 7.4），以在线 dudect 为准 |
| Q12 | 中途关机或断开 | 重开 WSL 后执行同一条 `./wsl_repro.sh all`，已完成的阶段和已有的 CSV 会自动跳过 |
| Q13 | 磁盘不足 | 全量约需 4 GB。可以先用 `REPEATS=1` 降低数据量，并在 RESULT.md 注明 |
| Q14 | M2 臂缺失（`platform-m2/unfixed/measure` 不存在） | fetch 阶段 M2 取件失败。看 `logs` 中的 fetch 段，修好后执行 `FORCE=1 ./wsl_repro.sh fetch && FORCE=1 ./wsl_repro.sh build && ./wsl_repro.sh p2m2` |
| Q15 | 想额外做仓库原生自检 | `cd ~/cry-wsl/repo && sh scripts/reproduce_all.sh quick --configs platform --samples 1000 --runs 1`（本机实测 EXIT=0）；**不要**运行 `full --execute` |
