# R15：第二架构（aarch64）12 格复现结果

**结论先行**：题面第 9 条的可选加分项「不同 CPU 架构」，此前在仓库里是**范围冻结**的
「不做」（理由：本机 macOS/ARM、交叉编译或模拟器不能冒充真实 x86_64 Linux 实测）。
本轮**做**了：在真实 aarch64（Apple Silicon，容器内 `uname -m` = `aarch64`，非 QEMU
模拟）上按与 x86_64 完全同源同口径的 12 格（3 臂 × 4 个优化级别）复现。

**关键发现**：**M1 的泄漏机制在 aarch64 上不复现**。同一份 liboqs 0.10.0 未修源码、
同一个 clang 18，在 x86_64 上产生秘密相关的条件跳转（Memcheck 上下文数 1/8/15），
在 aarch64 上**每一格都是 0 上下文、0 错误**——编译器把消息位选择编成了无分支的
算术 + 条件选择（`sbfx` / `and` / `csel`）。

这既给出了题面第 9 条的真实第二架构产物，也给既有结论加了一条**架构边界**：
M1（GHSA-f2v9-5498-2vpp / clangover）这条历史阳性机制是 **x86_64 特定的编译器产物**，
不是「ML-KEM 参考实现在别的架构上也泄漏」。

**本轮不改变任何既有判定**：不改 M1–M5 的结论，不动任何 Holm 家族，不进既有统计口径。
aarch64 的时间证据**不与 x86_64 裸金属合并、也不要求同号**。

---

## 1. 为什么本轮改口

仓库此前冻结的「不做第二架构」理由是（`docs/full-work-progress.md`）：
「本机 macOS/ARM、交叉编译或模拟器不能冒充真实 x86_64 Linux 实测」。这条理由针对的是
**把非 x86_64 的东西说成 x86_64 实测**。本轮的做法与之不冲突：

- 本轮**不声称**任何 x86_64 实测。x86_64 侧的全部结论仍只来自裸金属
  `nss-marker@10.144.144.5`。
- 本轮做的是**另一个架构**（aarch64）的对照，而题面第 9 条要的正是「不同 CPU 架构」。
- 跑的是**真 aarch64 指令集**的原生二进制，不是交叉编译产物、不是 QEMU 翻译执行。

仍然要如实写明的限制见 §5。

## 2. 口径

与 x86_64 的 12 格（[R09](../r09-optlevel-20261016/RESULT.md)）**同源同口径**：

| 项 | 口径 |
|---|---|
| 臂 | `m1unfixed`（liboqs 0.10.0 未修）、`m1fixed`（同版本 + 官方修复 982c762）、`m5ref`（mlkem-native 参考实现） |
| 级别 | `-O0` / `-O2` / `-O3` / `-Os`（与 R09 的 `OPTIMIZATION_LEVELS` 同） |
| 编译器 | clang 18（M1 机制本身就是 clang 引入的分支，gcc 不能替代） |
| 格的构成 | 实现、封装、探针**同一优化级别**（与 R09 的 cell 口径一致） |
| 探针 | 仓库既有的 `tools/historical_poison.c`（用 Valgrind 客户端请求把解封装私钥标成未初始化），不新增探针逻辑 |
| 判定量 | Memcheck 的**错误数**与**上下文数**（跨架构可比的确定性证据）、`poly_frommsg` 的分支形态。`SUMMARY.csv` 的 `poly_frommsg_branches` 列是**用宽松正则统计的匹配行数**（该正则会误计 `bic`/`bl` 这类同前缀助记符与 objdump 的分支预测注释），**既不是跳转条数、也不是秘密相关分支数**；真实跳转请按 §3.2 的反汇编逐条读 |
| 不做的事 | 不做密钥恢复、不产出 exploit；时间证据不跨架构合并 |

已修臂用**独立的 liboqs 副本**打 `docs/patches/liboqs-982c762.patch`，钉版树原件不动。

环境细节见 [ENVIRONMENT.md](ENVIRONMENT.md)。

## 3. 结果

### 3.1 秘密标记 Memcheck 的错误数与上下文数

**aarch64（本轮，`SUMMARY.csv`）**

| 臂 | `-O0` | `-O2` | `-O3` | `-Os` |
|---|---|---|---|---|
| `m1unfixed` | 0 / 0 | **0 / 0** | **0 / 0** | **0 / 0** |
| `m1fixed` | 0 / 0 | 0 / 0 | 0 / 0 | 0 / 0 |
| `m5ref` | 0 / 0 | 0 / 0 | 0 / 0 | 0 / 0 |

（格式：错误数 / 上下文数；原件在 `results/<arm>-<level>.valgrind.txt`。）

**x86_64 裸金属（R09 既有，`docs/evidence/r09-optlevel-20261016/memcheck/SUMMARY.tsv`）**

| 臂 | `-O0` | `-O2` | `-O3` | `-Os` |
|---|---|---|---|---|
| `m1unfixed` | 0 / 0 | **512 / 8** | **512 / 15** | **512 / 1** |
| `m1fixed` | 0 / 0 | 0 / 0 | 0 / 0 | 0 / 0 |
| `m5ref` | 0 / 0 | 0 / 0 | 0 / 0 | 0 / 0 |

（格式：错误数 / 上下文数。）

**逐格对照**：12 格里 **9 格一致**（全部 0），**3 格不一致**——且不一致的全部集中在
「x86_64 上的 M1 未修臂」：x86_64 在 `-O2`/`-O3`/`-Os` 上是 512 错误 / 8、15、1 个上下文，
aarch64 在同样三格上是 **0 错误 / 0 上下文**。

### 3.2 分支形态

aarch64 上 `m1unfixed` 的 `pqcrystals_ml_kem_768_ipd_ref_poly_frommsg`（原件在
`disasm/m1unfixed-*.poly_frommsg.asm`；**下面的地址是 `-Os` 一格**，四格的指令序列相同、
入口地址不同：`-O0`=4eec、`-O2`=4be0、`-O3`=4c78、`-Os`=4b2c）：

```
4b68:  ldrb   w11, [x1, x8]      ; 取消息字节
4b6c:  sbfx   w11, w11, #0, #1   ; 取第 0 位
4b70:  and    w11, w11, w10      ; 与 0x681 掩码
4b74:  sturh  w11, [x9, #-8]     ; 存系数
...
4be4:  csel   w11, wzr, w10, ge  ; 条件选择（无分支）
4bf4:  b.ne   4b68              ; 字节循环回边（计数）
```

函数体里的条件跳转只有：两处入口的**边界检查**（`b.ls`）与**字节循环的回边**
（`b.ne`，按公开计数跳转）。消息位的选择全部走 `sbfx` / `and` / `csel`——**无秘密相关分支**。
这就是 Memcheck 报 0 上下文的直接原因。

对照 x86_64（R09 既有反汇编）：M1 未修臂是 `bt %ecx,%r8d` + `jae`（秘密相关的条件跳转），
已修臂是 `bt` + `setb` + `call cmov_int16`（无分支）。**同一个源码在两个架构上编译出
了性质不同的代码**。

### 3.3 由此得到的两条结论

1. **M1 的泄漏机制是 x86_64 特定的编译器产物。**
   liboqs 0.10.0 的 `poly_frommsg` 写的是 `(msg[i] >> j) & 1`；x86_64 上 clang 把它
   编译成依赖消息位的条件跳转（这正是 GHSA-f2v9-5498-2vpp / clangover 那一族问题的
   形态），aarch64 上 clang 编译成无分支的算术。**因此「M1 未修臂在 aarch64 上仍泄漏」
   是不成立的**——aarch64 上它根本不泄漏。

2. **平台的秘密标记检测在两个架构上都能区分「有秘密相关分支」与「没有」。**
   M1 两臂两个架构用的是**同一份** `tools/historical_poison.c` 探针：x86_64 上报
   8/15/1 个上下文，aarch64 上报 0。
   **口径差异（必须说明）**：x86_64 的 **m5ref** 四格用的是另一个探针
   （`platform_m5_poison_cell --poison`），aarch64 的 m5ref 四格用的是
   `historical_poison.c`——**M5 参考路径的跨架构比较因此不是同探针对照**，
   只能由「两个架构上都是 0」这一**弱**结论支撑（0 上下文不依赖探针身份）。
   上述「检测是架构无关的」这一强结论**只对 M1 两臂成立**。

## 4. 能支持什么 / 不能支持什么

### 4.1 支持

1. 题面第 9 条的「不同 CPU 架构」这一项**已执行**，产出真实 aarch64 产物：12 格全部
   构建并测量，原件（Memcheck 日志、`poly_frommsg` 反汇编、汇总表、源码清单摘要）
   都在本目录。
2. **M1 机制的架构边界**：x86_64 上成立、aarch64 上不成立（同源码、同编译器版本、
   同优化级别）。
3. M5 参考实现与 M1 已修臂在两个架构上都是 0 上下文。

### 4.2 不支持、也不主张

1. **不是恒时证明**：Memcheck 的上下文数只回答「有没有秘密相关的条件跳转/内存访问」，
   不覆盖算术泄漏、缓存泄漏，也不覆盖 `multiplication`/`division` 类检查。
2. **时间证据不跨架构合并**：aarch64 是未锁频的虚拟化 Linux，噪声量级与 x86_64 裸金属
   锁频环境不同；本轮**没有**采 aarch64 的时间分布，也**不要求**两个架构同号。
3. **aarch64 侧不是裸金属**：跑在 Docker Desktop 的 Linux 虚拟机里（内核
   6.12.76-linuxkit），vCPU、无 cpufreq。因此 aarch64 侧不构成「第二个测量机」，
   只构成「第二个架构」。
4. **覆盖面有限**：只跑了 3 臂 × 4 级；`-O1`/`-Oz`/`-Og`、gcc 对照、以及 aarch64 上的
   M2/M3/M4 平台模块本轮都没做。
5. **不改任何既有判定**：M1–M5 的结论、四个 Holm 家族、R09 的可分辨性结论全部不变。
   本结果是**新增的、族外的**一层证据。
