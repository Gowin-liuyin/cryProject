# 恒时编码补丁的对照实测证据

功能源码提交：`e8f55e763dbec41801a8d7c1e9fd4e10477ee816`。构建时工作区完全干净：
`git status --porcelain` 为空，`tracked_delta_sha256` 为空内容摘要 `e3b0c442…7852b855`。

平台：Apple M5 / ARM64 macOS（Darwin 25.6.0）、Apple Clang 21、CMake 4.3.2 / Ninja、
RelWithDebInfo（`-O2 -g -DNDEBUG -std=c11`）、`CLOCK_MONOTONIC` 分辨率 1000ns、
未固定 CPU 亲和性与频率。configure.log、build.log、ctest.log 对应全新 build/mitigation 目录，
13 项 CTest 全部通过；compile_commands.json 保存实际编译命令。

## 对照设计

三个变体使用同一采集程序、同一公开种子 20260930、每类 5000 次（各 25000 条）。
record-checks.txt 用 `cut` 提取类别列并逐字节比较，确认三者的类别顺序完全相同，
因此输入构造、样本顺序与缓存/序列条件在三者之间一致。

- `vulnerable`：编码函数按消息位 `if/else`，函数级 `optnone,noinline`。
- `hardened`：**相同的** `optnone,noinline` 和相同循环结构，只把分支换成掩码选择。
- `reference`：上游常数时间实现，按所选配置正常优化（无函数级优化控制）。

vulnerable 与 hardened 之间只差分支本身，优化条件不变，因此差异不能归因于优化级别。

## 产物机制

三份反汇编中编码函数都位于 0x100002690：

| 变体 | 函数内条件分支 | 消息位处的指令 |
|---|---|---|
| reference | 仅 0x100002768 循环边界 `b.ne` | 无分支算术选择 |
| vulnerable | 循环边界 `b.lo` 与 0x1000026d8 的 `tbz w8, #0x0` | `tbz`，由消息位控制 |
| hardened | 仅 0x1000026a8 循环边界 `b.lo` | `and w8, w8, #0x1` 后接 `neg` 掩码 |

地址只对应本目录 binaries.sha256 与 record-checks.txt 记录的摘要，不跨构建复用。

## 固定检验结果

同一族 10 个预先规定的类别比较，Bonferroni 校正后单比较水平 1e-4。

| 变体 | 判定显著 | 类别均值极差 | 最大 \|rank z\| |
|---|---|---|---|
| vulnerable | 6 / 10 | 824ns（14581–15405） | 55.88 |
| hardened | 0 / 10 | 21ns（14531–14552） | 2.15 |
| reference | 0 / 10 | 41ns（14127–14168） | 1.31 |

缺陷版六项「恒定消息类 vs 变化消息类」全部显著，均值差 690.0–824.2ns、|z| 在 52.6–55.9 之间。
主比较 `message-zero:message-ones` 本次为均值差 -84.2ns、z=-3.83、p=1.26e-04，
略高于 1e-4 阈值因此判不显著；该项在不同采集之间反复越过阈值，属于小幅不稳定的次级差异。

防护版十项全部不显著，最大 \|z\|=2.15，残差方向不再一致（例如 `valid:message-ones`
均值差 -5.4ns 而 z=+0.71）。本次防护版的类别均值极差 21ns 小于参考版自身的 41ns，
说明类别相关差异已落到本机噪声量级；此前一次采集的防护版残差为 \|z\| ≤ 3.61、均值差 22–44ns，
因此残差幅度随运行波动，不能宣称已归零。

防护版整体比参考版慢约 400ns，原因是 `optnone` 关闭了该函数的优化，
这是为保持与缺陷版同一构建条件而有意付出的代价，不是防护方案的必要开销。
三个变体的整体水平也随机器负载在不同采集之间整体平移，因此只比较同一次采集内的类别差异。

## 结论边界

本组数据支持：在同一构建条件下去掉消息位分支后，类别相关的时间差异降到固定检验判不显著，
且降到与参考版噪声相当的量级。
不支持：防护版已被证明恒时。更大样本、其他主机或其他优化级别都可能重新分辨出差异；
本实验也未覆盖编译器自动向量化或真实 x86_64 Linux 产物。
