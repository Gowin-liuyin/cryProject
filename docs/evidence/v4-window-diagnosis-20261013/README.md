# v4 频率窗口覆盖率诊断

2026-10-13 在 `nss-m`（`systemd-detect-virt=none`，Linux 6.17.0-35-generic，`amd-pstate-epp`）上核对协议 `v4_group_confirmation_20261013` 第 6 节的窗口为什么达不到覆盖率 0.99。协议文本没有修改。只把 CPU2 和 SMT 兄弟 CPU18 的 `scaling_min_freq`、`scaling_max_freq` 请求为 4300000 kHz。没有写 governor、boost、EPP 或其他 CPU。进入和退出时 CPU2/18 都是 `powersave`、min `2982259`、max `5756452`。只读到的 CPU2 EPP 是 `balance_performance`，boost 是 `1`。

远端目录是 `/home/nss-marker/yhr/Cry/v4-window-diagnosis-20261013-050712`。这不是确认会话，没有解封装，没有使用确认种子。采样定义与 `v4_window` 相同：20 ms 读一次 CPU2 的 `scaling_cur_freq`，带是 `4257000..4343000` kHz，一次读数代表直到下一次读数的区间。

| 试次 | 结果 |
| --- | --- |
| 请求后立刻做 30 ms 紧循环 | 覆盖率 `0.4999851430072797`，首样本 `2982259` kHz |
| 含升频过程的 2 s 紧循环 | 覆盖率 `0.98999797167555814` 和 `0.96999661506708934` |
| 见到带内读数后再做 30 ms | 8 次中 7 次覆盖率为 1，1 次为 `0.49993487370168688` |
| 连续 3 次带内读数后交接 40 ms | 8 次中 7 次覆盖率为 1，1 次为 `0.50003370487582255` |

两秒连续采样见 `continuous-samples.csv`。101 个样本里带外的是起点 `5712950` kHz，以及负载已经上去之后的 `4251430` kHz 和 `4229670` kHz。后两个只比带的下沿低。因此，把计时进程推迟到请求已经反映在 `scaling_cur_freq` 里，只能去掉冷启动那一段；稳态里仍会离开冻结频带。短会话的覆盖率不是稳定地不低于 0.99 就是稳定地达到 0.99，而是会碰到这些读数。

确认采集仍不重跑。交替对照仍不开始。原确认记录留在 `docs/evidence/v4-confirmation-20261013`。机器策略已回到进入时的 32 路基线，诊断进程没有留下。
