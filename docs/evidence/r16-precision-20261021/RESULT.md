# R16：计时基准与频率自校准（物理精度 / 逐调用恒频的可行部分）

**结论先行**：此前登记为「未认证」的「物理精度与逐调用恒频」这个问题，本轮把它拆成
**可实测的四项**并全部实测。得到的分层结论是：

1. **TSC 速率实测 = 4 291 962 kHz（4.292 GHz）**，且**不随内核频率变化**——未锁频时
   核心跑在 2.98 GHz（powersave），TSC/核心 = 1.439；锁到 4.30 GHz 时 TSC 速率不变。
   也就是说：**用「标称频率」把 TSC 计数换算成纳秒，在未锁频机器上会引入 −31% ～ +32%
   的系统偏差**（第三方若这样换算会遇到；**平台自身不用这条换算**，见 §2.1）。
2. **rdtsc 的分辨率下界实测 = 42～43 个计数 ≈ 9.8～10.0 ns**（连续两次读数的间隔分布）。
   M1 未修臂的效应是几十纳秒量级——**只有 2～3 个分辨率单位**。这解释了为什么单次调用
   的计时噪声如此之大，也是「单次测量不可分辨、必须靠大样本」的直接原因。
3. **1 ms 短区间的隐含频率离散度实测**：2000 个 1 ms 区间，隐含频率的极差 348 kHz，
   相对极差 8.1e-5（0.008%），相对标准差 **5.4e-6**（锁频档；未锁频档 **7.5e-6**）。即在**毫秒尺度**上，
   TSC 与墙钟的比值是稳定的。
4. **逐调用（纳秒尺度）的物理恒频，本轮仍不可主张**：rdtsc 自身的分辨率下界就有约
   10 ns，用同一手段在纳秒尺度上**测不到**频率。这不是「测了没测到」，而是**这个
   方法在这个尺度上不适用**。

**本轮不改变任何既有判定**：不改 M1–M5 的结论，不动任何 Holm 家族，
不把「毫秒尺度稳定」说成「逐调用恒频」。

## 1. 方法

工具是仓库内的 `tools/platform_precision/tsc_calibration.c`（C 实现，见该目录 README）。
四个测项：

| 测项 | 做法 |
|---|---|
| TSC 速率 | 连续 60 秒读 TSC 与 `CLOCK_MONOTONIC`，算出每秒计数，与内核 `scaling_cur_freq` 对照 |
| 短区间隐含频率 | 反复取 1 ms 区间的 TSC 增量与墙钟增量，算出每个区间隐含的频率，给出分布与极差 |
| rdtsc 分辨率 | 连续两次 `rdtsc` 的最小间隔分布（4096 次） |
| 内核瞬时频率 | 测量期间读 `scaling_cur_freq`（2000 次） |

口径：

- **只读**：不写任何 cpufreq 节点；不加 sleep；不做固定拍数空转（区间长度用墙钟实测控制）。
- 原始逐区间值全部落盘（`unlocked-intervals.csv` / `locked-intervals.csv`），不删长尾。
- 时钟源 `CLOCK_MONOTONIC`，TSC 源 `RDTSC`（编译器插入序列化）。
- 两次运行：**未锁频**（机器默认状态）与**锁频**（平台控制器口径：boost=0、
  governor/EPP=performance、min=max=4300000 kHz、taskset 绑核、进入/采中/退出快照、
  `restore_match` 核对）。两次都在 **CPU2** 上跑（`taskset -c 2`），与平台采集同核。

## 2. 实测结果

原件：`data/`（摘要、逐区间 CSV、控制器 `terminal.json` / `during.json` /
`entry-probes.json`）。

### 2.1 TSC 速率与内核频率的关系

| 项 | 未锁频 | 锁频（控制器） |
|---|---|---|
| TSC 速率（kHz） | 4 291 964.002 | 4 291 962.533 |
| 墙钟时长（ns） | 60 000 000 007 | 60 000 000 015 |
| TSC 计数 | 257 517 840 140 | 257 517 752 033 |
| 结束时 `scaling_cur_freq`（kHz） | 2 982 259 | 2 982 259（已恢复原值） |
| TSC 速率 / 内核读数 | 1.439165 | 1.439165 |

**两种状态下的 TSC 速率几乎相同**（4 291 964.002 vs 4 291 962.533 kHz，相对差
3.4e-7；差值落在 60 秒计数的统计抖动量级内，不是「逐位相同」），
而内核报告的频率读数是 2.98 GHz。结论：**TSC 是定速计数器，与核心实际频率无关**。

- 锁频到 4.30 GHz 时，TSC 速率与目标频率的相对差 = (4 300 000 − 4 291 962)/4 300 000
  = **0.187%**——这是「用 TSC 计数换算纳秒」在锁频条件下的系统偏差上界。
- 若有人**用锁频标称的 4.30 GHz** 去换算未锁频档的核周期，按 cpu0 的实测频分布换算，
  偏差在 **−30.7% ～ +32.2%** 之间（min 2 982 259 kHz → 低估 30.7%；
  max 5 686 649 kHz → 高估 32.2%）；2.98 GHz 只是**结束时**的一次读数。**这项偏差不适用于平台自身的
  测量**：`src/measure.c` 与 `src/network_client.c` 都直接用
  `clock_gettime(CLOCK_MONOTONIC)` 取纳秒，不存在「TSC 计数 × 标称频率」的换算路径。
  另需注意：未锁频档运行期间 cpu0 的瞬时读数实测为 min 2 982 259 / p50 2 982 259 /
  p90 5 678 553 / max 5 686 649 kHz（均值 3 631 251 kHz），2.98 GHz 只是**结束时**的一次读数，
  运行中的实际频率高于它。

### 2.2 rdtsc 分辨率下界

| 项 | 未锁频 | 锁频 |
|---|---|---|
| 样本数 | 4096 | 4096 |
| min | 1 | 1 |
| p10 | 1 | 1 |
| p50 | **42** | **43** |
| p90 / p99 / max | 43 / 43 / 43 | 43 / 43 / 43 |
| mean / sd | 28.73 / 19.55 | 37.83 / 13.63 |

两次的中位数都是 42～43 个计数。按实测 TSC 速率 4.29196 GHz，43 个计数 =
**10.0 ns**，42 个计数 = 9.8 ns。min = 1 说明偶尔两次读数只隔 1 个计数（读取被流水
重叠），所以「最小间隔」不能当作分辨率下界，**p50 才是**。

对照：M1 未修臂的效应在几十纳秒量级（R09 的 `m1unfixed-Os` 一格的合并 Δ_pool = −26.16 ns，95% CI [−37.51, −14.81]；这是**该格**的数值，不是「M1 未修臂」各格的通值），即
**约 2.6 个分辨率单位**。这就是为什么单次调用几乎测不出来。

### 2.3 1 ms 短区间的隐含频率

| 项 | 未锁频 | 锁频 |
|---|---|---|
| 样本数 | 2000 | 2000 |
| min（kHz） | 4 292 045 | 4 292 045 |
| p50（kHz） | 4 292 092 | 4 292 131 |
| max（kHz） | 4 292 393 | 4 292 393 |
| mean（kHz） / sd | 4 292 078.6 / 32.21 | 4 292 121.9 / 23.34 |
| 极差（kHz） | 348 | **348** |
| 相对极差 | 8.1e-5 | **8.1e-5** |
| 相对标准差 | 7.5e-6 | **5.4e-6**（本表该行由 sd/mean 重算；摘要文件里 `short_interval_implied_frequency_relative_sd` 按 6 位小数写成 0.000008 / 0.000005，**全文一律用重算值 7.5e-6 / 5.4e-6**） |

即：在 1 ms 窗口上，TSC 与墙钟的比值**相对标准差 5.4e-6（0.00054%，锁频档）**、**极差 8.1e-5（0.008%，半量程 ±0.004%）**，
极差 348 kHz（0.008%）。**锁频与未锁频在这一项上没有可见差别**——因为 TSC 本身
是定速的，这项测的是「TSC 与墙钟的相对漂移」，不是「核心频率的稳定」。

### 2.4 内核瞬时频率读数的一个口径问题（必须说明）

工具读的是 `/sys/devices/system/cpu/cpu0/cpufreq/scaling_cur_freq`，而控制器锁的是
**CPU2**。因此这一列读数是**一个未锁频的 CPU 的瞬时反馈值**，不是被测 CPU 的频率：

**锁频档**（锁频运行期间 cpu0 的瞬时反馈读数）：

| 项 | 值 |
|---|---|
| 样本数 | 2000 |
| min | 2 152 658 kHz |
| p50 | 2 982 259 kHz |
| max | 4 308 557 kHz |
| mean / sd | 2 979 131 / 216 579 kHz |

这解释了为什么它在锁频运行期间仍有大幅波动——**它本来就不该跟着 CPU2 的锁频走**。
这条读数**不能**用来支持「被测 CPU 恒频」的任何陈述。本轮关于被测 CPU 频率的
有效证据是控制器的 `during.json`（20 次探针全部落在 4 300 000 ± 2%、跨度 ≤ 50 000 kHz
的放行判据内）与 `entry-probes.json`。

## 3. 能支持什么 / 不能支持什么

### 3.1 支持

1. **TSC 速率的实测值 4 291 962 kHz**，以及「TSC 速率与核心频率无关」这一事实。
2. **用 TSC 计数换算纳秒的系统偏差**：锁频条件下 0.187%；未锁频条件下按 cpu0 的实测频分布
   换算，偏差在 **−30.7% ～ +32.2%** 之间（min 2 982 259 kHz → 低估 30.7%；
   max 5 686 649 kHz → 高估 32.2%）——**30% 既不是上界也不是典型值**。
   **平台自身不走这条换算**（`src/measure.c`、`src/network_client.c` 直接用
   `clock_gettime(CLOCK_MONOTONIC)`），该偏差是给「第三方按标称频率换算」时的提醒。
3. **rdtsc 的分辨率下界 ≈ 10 ns**（p50 42～43 计数）。
4. **1 ms 尺度的相对漂移**：隐含频率相对标准差 5.4e-6、极差 8.1e-5（均为**锁频档**的值；未锁频档为 7.5e-6 与 8.1e-5）。
5. **测量工具本身只读**（不写任何 cpufreq 节点）；锁频那一档的频率写入由**平台控制器**执行，
   结束时 `restore_match=yes`、`worker_drained=true`，频率策略已恢复原值——即「本轮没有留下
   未恢复的频率改动」，而不是「本轮没有任何进程写过频率」。

### 3.2 不支持、也不主张

1. **不主张「逐调用恒频」**：本轮只在 **1 ms 尺度**上给了相对漂移的实测数。
   纳秒尺度上，rdtsc 自身 ~10 ns 的分辨率下界使该尺度的频率**不可观测**——
   这不是「测了没测到」，而是方法在此尺度不适用。
2. **不主张物理误差界**：本轮全部是**工程观测**（同一台机器、同一计数器、同一墙钟源），
   不构成对频率物理行为的证明，也不构成对「某次解封装耗时是多少纳秒」的物理认证。
3. **不主张平台已锁频的 12 格结论需要按本轮数值重算**：R02/R08/R09 的判定与统计
   **不变**。本轮只是把「为什么必须锁频」和「计时分辨率有多粗」这两件事量化了。
4. **不覆盖多核/迁移**：全部测量绑定在 CPU2（`taskset -c 2`），未覆盖核间迁移、
   SMT 兄弟线程、超线程争用等情形。
5. **不覆盖内核频率反馈的物理机制**：只读了 `scaling_cur_freq` 这一个用户可见接口，
   没有读 MSR、没有核对 `amd_pstate` 的实际工作点。
6. **锁频档的 cpu2 侧频率证据只有控制器的那一份**：工具自己读的是 cpu0（见 §2.4），
   被测 CPU2 的频率只有 `during.json` / `entry-probes.json` 里的控制器探针为凭；
   **未锁频档没有 cpu2 侧的频率证据**（该档根本没锁频），因此两档之间「核心频率不同」
   这一前提在未锁频档是由 `scaling_cur_freq` 的读数**间接**支撑的。

## 4. 目录内容

| 路径 | 内容 |
|---|---|
| `data/unlocked-summary.txt` | 未锁频摘要（TSC 速率、rdtsc 分辨率、短区间隐含频率、内核读数） |
| `data/locked-summary.txt` | 锁频摘要（同上） |
| `data/unlocked-intervals.csv` | 未锁频的逐区间原始值（2000 行） |
| `data/locked-intervals.csv` | 锁频的逐区间原始值（2000 行） |
| `data/locked-terminal.json` | 控制器终态（`restore_match=yes`、`worker_drained=true`） |
| `data/locked-during.json` | 采集期间的频率读数与策略项（**cpu2** 侧） |
| `data/locked-entry-probes.json` | 进入时的 20 次频率探针 |
| `data/*-status.txt` | 两次运行的退出码 |
| `data/locked-controller.log` | 控制器输出（**本次为空文件**：控制器本身不写 stdout） |

## 5. 复现

```sh
cmake -S tools/platform_precision -B build/platform-precision -DCMAKE_BUILD_TYPE=RelWithDebInfo
cmake --build build/platform-precision
ctest --test-dir build/platform-precision --output-on-failure
# 裸金属上：
./build/platform-precision/tsc_calibration 60 1000000 2000 intervals.csv summary.txt
```

锁频那一档由平台控制器以 worker 身份执行 `tsc_calibration`（原生 ELF、在 Cry 之内、
`taskset` 绑到 CPU2），控制器负责锁频、进程回收与恢复。
