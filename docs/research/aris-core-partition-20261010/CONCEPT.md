# 少量核预留的内核分区候选方案

2026-10-10。状态：KERNEL_ROUTE_SUPPORTED，管理实现和实际预演未完成。[只读原件](../../evidence/core-cpuset-preflight-20261010/README.md)确认相关接口与CPU2/18拓扑，不构成root预留成功或R02资格。

旧609行方案继续禁用，不移动其封存stage或改写旧证据。不采用逐线程批改亲和性的替代方案：新任务继承、身份复用和并发修改使其完整恢复难以封闭；只绑定自有进程也不能证明排他。

根据[Linux6.17分区接口](https://docs.kernel.org/6.17/admin-guide/cgroup-v2.html#cpuset)，候选使用根下有效local isolated分区，仅分出CPU2/18这一个物理核，其余30个逻辑CPU供普通任务使用；恢复为member后由内核归还。两名同模型代理中的资源审查者核查了该路线，判断值得限定预演，不代表已经验证实际执行。

项目工程安排是一个自有guard组和一个自有probe分区；只迁移自有守护及空任务，不逐一改其他服务属性、线程掩码或systemd配置文件。源码、root私有恢复快照、日志、缓存、临时文件及人工恢复入口全部落盘`/home/nss-marker/yhr/Cry`。资源状态只通过内核的虚拟cgroup接口调整，不以临时文件为理由在/run存放项目资料，也不新建systemd单位。

实现前必须满足以下门槛：

1. 重新核对root权限、真实宿主与cgroup命名空间、控制器、所有相关现有分区和CPU/内存节点状态；本次仅查三单位，不替代完整新快照。新guard/probe名字和目录须原先不存在，已有配置或同期改变不符合同即停止。
2. guard先脱离SSH会话cgroup，核对自身身份、有效CPU、恢复权限与实际可用返回位置，完成独立握手后才允许建立probe分区。仅setsid或双fork不足以证明守护独立。
3. 分区写后必须读到有效isolated而非invalid，排他CPU恰为2/18，根及其他普通分支有效CPU排除2/18。监视热插拔、失效及同期配置变化；缺观察不得继续。
4. 恢复先停止自有控制器继续写，回收自有probe任务，再降为member，核对原有效集合并清理probe；guard仅迁移自身并清理自有组。保留原请求值、用户亲和性及其他应用设置，不能把全机运行状态说成可回滚。
5. 事前固定正常结束与父进程受控终止两种恢复检查，以及执行、恢复和总预算；全部失败保留。守护本身被杀、OOM或整机故障不享有自动恢复保证，Cry内人工恢复入口必须先可审查。

第一阶段只做有限管理预演和一次空任务，核查预留及恢复，不运行密码或计时实验。直接内核操作的systemd单写者协调风险须处理；root可写不等于获得普通用户委派。IRQ、绑定内核线程、共享缓存/内存/功耗、频率及时钟精度另行核查，不能把一个核的普通任务排他改称完全无噪声或锁频。

当前缺的是经过审查的具体实现和实际恢复证据，而非再次索取用户已经授予的密码交互或管理员授权。无新后台句柄可等待；旧KVM指纹问题与此主机资源路线分别处理。
