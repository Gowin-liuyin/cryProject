# 裸金属计时控制候选方案

2026-10-09。仅供控制窗口和资源归属确认，尚未执行。主机nss-m的32个逻辑CPU对应16个物理核心，CPU2与18为同一物理核心的两个SMT线程；当前每个逻辑CPU各有policy，amd-pstate-epp、powersave，允许范围2982259至5756452kHz，boost为1。

第一候选是在取得该物理核心的专用窗口后，只把采集进程限制到CPU2，预留其SMT同伴18，先核对两者policy及实际可写权限。保存原驱动、governor、EPP、频率上下限及boost状态；候选将两份policy的上下限暂设为3000000kHz，保留governor/EPP及全局boost。3GHz只是落在当前允许范围内、靠近下界的低热负载配置候选，不是时间容许界、安全阈值或已证明可实现的恒定频率。

若只获得其他核心，按实际拓扑选同一核心的两个逻辑线程，不照抄CPU2/18。若主机正在共享而不能保证预留，就不改这些设置；可继续软件检查和只读解释。此方案不关闭SMT、不改全局boost或IRQ/系统隔离，不停止其他进程。若后续证明必须改变全局项目，应另说明全机影响和恢复步骤，并取得对应控制窗口。

执行前需有完整的可恢复快照及恢复权限；写入顺序必须始终满足最小值不高于最大值。任何读写或恢复验证失败都停止正式采集，留下原值及退出，不能隐藏失败或把未知状态写成已锁频。结束及异常退出都恢复两份policy原值并回读核对；不得遗留新配置。

单纯把上下限写成相同、读取瞬时频率或指定taskset都不证明持续控制。CPUFreq的scaling_cur_freq可能反映请求值，应另取得可用的硬件频率反馈及其采样/误差依据，在正式窗口外留证；目标频率允许带和目标计时精度仍须事前定义。低负载快照也不证明独占。依据见[Linux CPU性能缩放文档](https://docs.kernel.org/admin-guide/pm/cpufreq.html)与[AMD P-state文档](https://docs.kernel.org/admin-guide/pm/amd-pstate.html)。

当前待用户确认资源归属/控制窗口，并待实际权限和硬件反馈能力核对。频率方案准备不使R02/R04自动签收，良性参考任务的目标、有效统计方法、容许界和完整预算继续按NEXT_VALIDATION_PROTOCOL确定。没有这些门槛，不启动正式计时。

同日用户进一步提出只用几个核的路线；不再把整机独占作为门槛。后续[单物理核预留方案](CORE_RESERVATION_PLAN.md)限定CPU2/18，已核对本机普通权限、sudo策略与systemd255能力；普通任务预留和内核isolated分区明确区分。尚未执行预留或频率写入，正式窗口的冲突与恢复检查继续保留。
